# 判断が要る観点

機械的検査で拾えない項目をここに置く。各項目は「何を見るか」と「出典」を持つ。
出典は Anthropic の公式ガイドである。

- Opus 5: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5
- Sonnet 5: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5

読む順は上から下でよい。1項目ごとに「該当なし」も明記して、飛ばしたのか見たのかを残す。

## 1. 過剰検証を招く記述

| 見るもの | 判断基準 |
|---|---|
| モデル自身への再確認指示 | Opus 5 は指示なしで自己修正する。「回答前に再確認」「ダブルチェック」は費用だけ増える。**削除する** |
| 決定的なツール手順 | `lint を実行してからコミット`、`push 前に divergent() を確認` は検証指示ではなく手順である。**残す** |
| 独立した検証フェーズ | 「非自明なタスクには最終検証ステップを設ける」型の足場は Opus 5 では過剰検証になる。**削除する** |
| サブエージェントによる検証 | Opus 5 は「自分の作業の検証にサブエージェントを使うな」と明示する。ただし writer-verifier 型の多エージェント協調自体は有効とされる。**設計意図を確認してから判断する** |

役割を分けた敵対的レビュー(一次レビュー → 反証)は、後段が「自分の作業」ではなく
「別エージェントの出力」を検証するため、この禁止に直接は当たらない。
費用に見合うかだけを実測で判断する。

## 2. レビュー系資産の recall

| 見るもの | 判断基準 |
|---|---|
| 「重大な指摘のみ」「保守的に」「重箱の隅をつつくな」 | Sonnet 5 / Opus 5 は literal に守るため報告数が落ちる。発見段階では全件出させ、絞り込みは別の段でやる |
| 発見段階の指示 | 「確信度と深刻度を添えて全部出す。絞り込みは後段がやる」と書けているか |
| 単段で自己フィルタさせる場合 | 「重要なもの」ではなく「誤動作・テスト失敗・誤った結果を招くもの。純粋なスタイルや命名の好みだけ除く」のように境界を具体で書く |

## 3. 冗長さの制御

| 見るもの | 判断基準 |
|---|---|
| 会話応答の長さ | Opus 5 の既定応答は前世代より長い。effort を下げても表示応答は短くならない。長さは明示的に指示する |
| 書き出す文書の長さ | ディスクに書くレポートや Markdown も長くなる。「中身は網羅し、埋め草の節・重複した要約・定型文で膨らませない」を入れる |
| 進捗ナレーション | Opus 5 は実況しやすい。出してほしい更新の形を肯定形の例で書く。「〜するな」より効く |
| output-styles の方針 | 綿密な説明を求めるスタイルは Opus 5 の既定の冗長さと重なる。意図した設計なら維持し、その旨を記録する |

## 4. スコープと委譲

| 見るもの | 判断基準 |
|---|---|
| スコープの制約 | Opus 5 は頼まれていない手順を足すことがある。「頼まれた範囲を、頼まれた粒度で出す」を明示できているか |
| 委譲の条件 | 「本当に独立した大きな作業だけに委譲する。数回のツール呼び出しで終わる作業は委譲しない」を書けているか |
| 決定的な上限 | `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` / `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` を設定しているか(Claude Code 2.1.217 以降) |

## 5. effort とモデルの割り当て

| 見るもの | 判断基準 |
|---|---|
| 前世代から引き継いだ effort | Opus 5 では low / medium が主要な費用レバーになった。引き継ぎ値は実測で掃引し直す |
| 読み取り専用の調査役 | low で品質が保てるか実測する |
| 難しい実装・エージェント作業 | xhigh へ上げる価値があるか実測する |
| モデル名 | 現行の Claude 5 系(fable / opus / sonnet)と Haiku 4.5 を指しているか |

数値を1箇所に集約している資産(`skills/agent-routing/data/roles.json` など)は、
掃引後にそこだけ書き換えれば全経路へ伝わるかを確認する。

## 6. 命令の literal さ

Sonnet 5 は指示を字義どおりに取り、1項目から他項目へ黙って一般化しない。

| 見るもの | 判断基準 |
|---|---|
| 適用範囲の書き方 | 「すべての節に適用する。最初の節だけではない」のように範囲を明示しているか |
| 例示だけで済ませた規則 | 例が規則の全体を表しているとモデルが読める書き方になっているか |

## 7. Skill / SubAgent の起動条件

| 見るもの | 判断基準 |
|---|---|
| description | モデルは description だけで起動を判断する。「何をするか」と「いつ使うか」の両方が要る |
| 起動しない条件 | 誤起動が起きている資産には、起動しない条件も書く |
| 重複 | 同じ役割の資産が複数あると、モデルはどちらを選ぶか決められない。統合するか、境界を description に書く |

## 8. 廃止された前提

| 見るもの | 判断基準 |
|---|---|
| `temperature` / `top_p` / `top_k` | Sonnet 5 では非既定値が 400 エラーになる。文体は system prompt で指示する |
| 手動 extended thinking | `thinking: {type: "enabled", budget_tokens: N}` は Sonnet 5 で削除済み。adaptive thinking + effort に置き換える |
| thinking を無効化する運用 | 無効化すると tool_use がテキストとして漏れる・内部 XML タグが出る事故がある。effort を下げる方を選ぶ |
| 「考えるな」「推論するな」型の指示 | タグ漏れを増やす。削除する |
