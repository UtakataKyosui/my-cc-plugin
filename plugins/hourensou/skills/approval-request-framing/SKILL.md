# approval-request-framing 依頼の種別を決めてから書く

## 何のためのスキルか

リアクションだけが返ってきたとき、それが了承なのか受領なのか判断できずに手が止まることがある。原因はリアクションの側ではなく、送ったメッセージが何を頼んでいるか決まっていなかったことにある。末尾が「ご確認いただければ幸いです」なら、頼んだ動詞は確認である。そこに承認の意味まで読み取ろうとするから曖昧になる。

このスキルは、送信前に種別を1つ選ばせ、末尾の一文をそれに合わせることで、返ってきた反応の意味を一意に決める。

## 原則

- 決めるのは記号の意味ではなく、自分が何を頼んでいるかである。
- 曖昧さの解消を相手の作法に求めない。相手に新しいリアクションを覚えてもらう提案は、既存の使い方が不十分だったという含意を持つ。負荷はこちらの書き方に置く。
- 承認のリアクションには帰結を持たせる。承認後に何が起きるかを書いておけば、そのリアクションは読んだだけでは成立しなくなる。

## 手順

### 1. 種別を判定する

送るメッセージが次のどれなのかを1つ選ぶ。迷ったら、返事がないまま先に進めるかどうかで決める。進めるなら共有か確認、進めないなら承認である。

| 種別 | 末尾に書く一文 | 返ってきたリアクションの意味 | 反応がないときの動き |
|---|---|---|---|
| 共有 | ご参考まで共有いたします | 読んだ | そのまま進む |
| 確認 | ご認識と相違がないかご確認ください | 読んだ | 相違の指摘がなければ進む |
| 承認 | よろしければサムズアップをお願いします | 了承した | 進まない。催促する |

### 2. 末尾の一文を書く

選んだ種別の行をそのまま末尾に置く。承認以外の種別では、リアクションを求める文言を書かない。書かないこと自体が確認どまりであることの印になる。

### 3. 承認のときだけ3つ足す

1. 承認後に何をするかを書く。例として、了承いただけましたら先方へ提示します、と書く。
2. 他の話題を同じメッセージに入れない。承認事項と共有事項が同居すると、リアクションが何に付いたのか事後に判定できなくなる。
3. 緩い期限を添える。例として、明日の定例までにご確認いただけますと幸いです、と書く。無反応だった場合の意味もこれで決まる。

### 4. 曖昧なリアクションが返ってきたときの書き方

すでに種別を決めずに送ってしまい、意味の分からないリアクションが返ってきた場合は、相手の使い方を問う形にしない。こちらの解釈として受け取ったと述べ、念のため了承かどうかを尋ね、あわせて今後の進め方への同意を求める。1回のリアクションで解釈の確認と運用の合意を両方取れる形にする。

この1件がそのまま前例になる。運用を文章で定義するのではなく、依頼文つきのメッセージにリアクションが付く実例を1つ作れば、次からは前回と同じですで通る。

## やらないこと

- 承認用に新しい記号を導入する提案はしない。理由は原則の2つ目にある。
- 種別を2つ兼ねたメッセージを作らない。承認を求めるなら、そのメッセージは承認だけを求める。

## 関連

- 期限の遅れそのものを報告する文面は `skills/deadline-hourensou` で作る。このスキルは依頼の種別と締めの一文だけを扱う。
- 相手の非を示唆しない書き方の背景は auto memory の feedback-no-blame-framing にある。
