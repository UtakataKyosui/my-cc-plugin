# claim-verifier 文書の主張を出す前に検証する

## 何のためのスキルか

原因の説明、規約の要約、実装状況、数値のような主張は、書いた本人が正しいと思っているまま文書に残る。読み手が気づいて訂正するのでは、読み手の時間を使っている。このスキルは、文書を出す直前に主張を 1 つずつ取り出し、根拠を探し、根拠の強さに合わせて文を直す。

判定の主体はサブエージェント `agents/claim-verifier.md` に置いてもよい。文書を書いた側と検証する側を分けると、書いた側の思い込みを引き継がずに済む。

## 手順

### 1. 主張を抜き出す

文書を読み、真偽を問える文を全部列挙する。次の形が該当する。

| 主張の形 | 例 |
|---|---|
| 原因や経緯 | リベースの事故で変更が消えた |
| 規約や制限 | 出典表示は画面内に常時必要である |
| 実装状況 | カバレッジ計測は実装済みである |
| 数値 | 27 項目、3 人日、9 件の PR |
| 挙動の限界 | 日本全体が見える縮尺まで縮小できない |
| 帰属 | この規約は Wiki のコードルールに書いてある |

意見や提案は対象にしない。「〜すべき」「〜がよい」は判定しない。

### 2. 主張ごとに一次情報を探す

| 主張の種類 | 探す場所 |
|---|---|
| PR や Issue の経緯 | `gh pr view <n> --json title,body,reviews,commits`、`gh issue view <n> --comments` |
| コードの挙動や実装状況 | 該当ファイルの Read、Grep。テストがあればアサーションまで読む |
| 外部の規約や仕様 | WebFetch で原文の該当箇所を読む。二次情報の要約で済ませない |
| 顧客や相手の発言 | 元のメッセージの原文。要約ではなく文言 |
| 数値 | 集計コマンドを再実行して数え直す |

### 3. 判定する

| 判定 | 条件 | 文の扱い |
|---|---|---|
| VERIFIED | 一次情報が主張と一致する | そのまま残す。根拠を控えておく |
| UNVERIFIED | 一次情報が見つからない、または読めない | 最も弱い言い方に直すか削る。残す場合は未確認と明記する |
| CONTRADICTED | 一次情報が主張と食い違う | 一次情報に合わせて書き直す。元の文は残さない |

不確実なものを VERIFIED に寄せない。読み手に「未確認」と伝えるほうが、後で訂正するより安い。

### 4. 検証表を作る

```
| 主張 | 判定 | 根拠 |
|---|---|---|
| PR #4322 は表を 27 行に拡充した | VERIFIED | gh pr view 4322 --json files の diff |
| 変更が消えた原因はリベースである | CONTRADICTED | gh pr view 4312 の reviews にレビュー判断による削除が記録されている |
| 日本全体が見える縮尺まで縮小できない | UNVERIFIED | 顧客の原文にこの記述がない。削除する |
```

根拠の列には、`gh` のコマンドと出力の該当箇所、ファイルパスと行番号、URL のどれかを書く。「確認した」だけでは根拠にならない。

### 5. 文書を直して返す

判定に従って文書を修正し、検証表とあわせて返す。UNVERIFIED と CONTRADICTED が 1 件でも残ったまま「検証済み」と報告しない。

## サブエージェントに任せるとき

```
Agent(subagent_type="claim-verifier", prompt="次の文書の主張を検証して。<文書本文>。参照できるリポジトリは <path>、関連 PR は #<n>。")
```

サブエージェントは読み取り専用で、文書の修正案と検証表を返す。文書への反映は呼び出し側が行う。

## 罠

- `gh pr view` の既定出力には reviews が含まれない。経緯を追うときは `--json reviews,comments,commits` を明示する
- 顧客向け文書の「制限」や「仕様」は、書き手が補った推論であることが多い。原文に同じ内容の文があるかを、語のレベルで突き合わせる
- 数値は転記のたびにずれる。文書に書く直前に数え直す
