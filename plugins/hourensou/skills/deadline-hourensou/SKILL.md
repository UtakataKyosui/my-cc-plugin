# deadline-hourensou 期限報連相のドラフト作成

## 何のためのスキルか

期限に関わる報告・連絡・相談は、遅れの検知、文面の作成、相談の切り出しのどれもが後回しになりやすい。このスキルは、junct と gh-wheel にすでにある実績データから遅延リスクを機械的に判定し、送るだけの状態の文面まで作ることで、後回しの原因を取り除く。

文面はドラフトとして提示し、送信はユーザーに委ねる。Slack への自動送信はユーザーが明示的に依頼した場合に限る。

## 原則

- 悪い報告ほど早く出す。遅延の報告は、遅延が確定してからではなく遅延の可能性に気づいた時点で出す。
- 進捗ゼロも報告の対象にする。動きがないことを伝えるだけで、受け手は前提を更新できる。
- 完璧な文面より速さを優先する。3 行の暫定報告は、明日の丁寧な報告より価値が高い。

## 手順

### 1. 状況を収集する

1. `date +%F` で今日の日付を取る。
2. `get_daily_plan_comparison({ date: <今日> })` で今日の計画と実績の差を取る。
3. 対象タスクが分かっていれば `get_task_time_summary({ task_id })` で見積もりと実績を取る。分かっていなければ `list_projects` と `list_tasks({ project_id })` で対象を特定する。
4. GitHub 側の期限情報が必要なら `gh wheel task` と `gh wheel graph --milestone <マイルストーン>` で Issue/PR の状態と依存関係を取る。マイルストーンの期日、ブロックしている依存 Issue を確認する。

### 2. リスクを判定する

`estimated_hours` は時間、`completed_seconds` は秒なので、単位をそろえてから消化率を計算する。

| 消化率 | 判定 | 取る行動 |
|---|---|---|
| 70% 未満で作業も順調 | 順調 | 定期報告のみ |
| 70% 以上 100% 未満で未完 | 注意 | 連絡ドラフトを作る |
| 100% 以上で未完 | 遅延 | 報告ドラフトを必ず作る |

消化率が低くても、依存 Issue のブロックや仕様の不明点で手が止まっているなら相談モードを選ぶ。

### 3. モードを選ぶ

- 報告: 完了、定期進捗、遅延確定を伝える。
- 連絡: 遅延の見込み、予定の変更、前提の変化を先回りで共有する。
- 相談: 詰まっている問題について判断や助けを求める。

### 4. 文面をドラフトする

Slack 用テキストと口頭用メモの両方を作る。数値と日付は手順 1 で取った実データから埋め、推測で書く箇所には「要確認」と明記する。

#### Slack 用テンプレート（報告・連絡）

```
【<タスク名> 進捗<報告|連絡>】結論: <順調|遅延見込み|遅延> です。
- 現状: 見積もり <X>h に対して実績 <Y>h（消化率 <Z>%）、残作業は <内容>
- 完了見込み: <日付>（当初予定: <日付>）
- 影響: <遅れた場合に影響する範囲。なければ「なし」>
- 次のアクション: <自分が次にやること>
- お願い: <判断・確認してほしいこと。なければ「共有のみです」>
```

#### Slack 用テンプレート（相談）

```
【<タスク名> 相談】<何の判断が欲しいか> を相談させてください。
- 状況: <何が起きているか 1〜2 文>
- 試したこと: <試行 1>、<試行 2>、<試行 3>
- 分かったこと: <切り分けの結果>
- 選択肢: A) <案とコスト> B) <案とコスト>
- 自分の考え: <どちらに傾いているかと理由>
- 期限: <この判断がいつまでに必要か>
```

#### 口頭用メモ

ミーティングや朝会で 30 秒で話せるよう、次の 3 点だけを書く。

1. 結論を 1 文で言う。順調か、遅れそうか、助けが要るか。
2. 根拠の数字を 1 つだけ添える。消化率か完了見込み日。
3. 相手に求めることを言う。共有だけなのか、判断が欲しいのか。

### 5. 確認して仕上げる

ドラフトを提示し、AskUserQuestion で宛先のトーンと不足情報を確認して手直しする。ユーザーが後で送ると言った場合も、暫定ドラフトはその場で完成させて残す。文面を作り直す手間が翌日の先延ばしの原因になるためである。

## 罠

- `estimated_hours` が未設定のタスクは消化率を計算できない。Skill `junct-workflow:junct-estimate` の手順で先に見積もりを記録するよう促す。
- 消化率だけでは、残作業が想定より膨らんだケースを検知できない。残作業の見込みをユーザーに一言確認してから完了見込み日を書く。
- 相談ドラフトで試したことを盛りすぎない。3 件を超える場合は切り分けに効いたものだけ残す。
