# standup-progress-note 定例で読み上げる進捗報告を作る

## 何のためのスキルか

書き言葉の報告書と、定例で読み上げる報告は別物である。報告書は後から参照するために事実を網羅するが、定例の報告は聞いている人がその場で次の判断をするためにある。表とチェックボックスで整理された報告書をそのまま読み上げても、聞き手には項目の切れ目が伝わらない。

このスキルは、報告書の内容をワークストリームごとの3〜5行の箇条書きに組み替え、聞き手が知りたい4つのことを決まった順で並べる。長さと形式は `scripts/standup.py` が機械的に検査する。

## 出力の形式

先頭に日付と会の名前を書き、1行空けてワークストリームを並べる。ワークストリーム名を1行で置き、次の行から3〜5行の箇条書きにする。

```
4/8 内部定例

開発ルールの整備
- PR #12 をマージし、レビュー観点の公開とテンプレートの改訂が完了しました
- 残りの手順書の追随は、今日中にチケットを切ります
- 追随の結果は明日の定例で共有します

テスト環境の構築
- PR #15 を作成し、レビュー依頼まで出しました。CI はすべて成功しています
- 自動レビューの指摘 6 件を今日中に反映して、マージしたいです
- 確認したいこと: うち 2 件はジョブの作り替えを伴います。この PR で直すか、別チケットに切るかを相談させてください
```

## 各項目に入れる4つのこと

順番を変えない。聞き手は前の報告との差分を先に知りたい。

| 項目 | 書くこと | 省略 |
|---|---|---|
| ここまで何をしたか | 前回の報告以降に終わったこと。前回「今日中にやる」と言ったことの結果を必ず含める | 不可 |
| 次に何をするか | 次の1手。複数あるときは行を分ける | 不可 |
| いつまでにやるか | 今日中、明日まで、連休前の 9/18 までなど、聞き手がカレンダーで指せる形 | 不可 |
| 共有すべき課題や確認事項 | その場で判断を仰ぎたいこと。行頭に「確認したいこと:」を置き、そのワークストリームの最後の行にする | 可 |

1行に1つのことだけを書く。いつまでにやるかは、次に何をするかと同じ行に入れてよい。

## 検査項目

`scripts/standup.py validate <file>` が次を見る。違反があると終了コード 1 を返し、ルール名と行番号を出す。

| ルール | 既定値 | 上書きする引数 |
|---|---|---|
| bullet-count | 1ワークストリームあたり3〜5行 | `--min-bullets` `--max-bullets` |
| bullet-chars | 1行 100 文字以内 | `--max-bullet-chars` |
| workstream-chars | 1ワークストリームの箇条書き合計 300 文字以内 | `--max-workstream-chars` |
| total-chars | 全体 800 文字以内。超えても警告だけで止めない | `--max-total-chars` |
| header-date | 1行目が「9/17 内部定例」の形である | なし |
| header-blank | 2行目が空行である | なし |
| no-markdown | アスタリスク、バッククォート、半角の縦棒を含まない。箇条書きの記号はハイフン1つである | なし |
| deadline | 各ワークストリームに期限を表す語が1行以上ある | なし |
| confirm-once | 「確認したいこと:」の行が1ワークストリームに2つ以上ない | なし |
| confirm-last | 「確認したいこと:」がそのワークストリームの最後の行である | なし |
| trailing-space, crlf | 行末に空白がなく、改行が LF である | なし |

既定値は実測から決めた。1行の最長が 86 文字、1ワークストリームの最大が 233 文字、全体が 566 文字だった報告を基準に、それぞれ切り上げている。

## 手順

### 1. 材料を集める

その日の内部定例レポートがあればそこから起こす。ない場合は junct の実績と gh で PR と Issue の状態を確認してから書く。報告に書く番号と日時は確認した値を使い、記憶から書かない。

### 2. 雛形を作る

前回のファイルがあれば、ワークストリーム名を引き継ぐ。プラグインの実パスは `claude plugin list` や `${CLAUDE_PLUGIN_ROOT}`（フック実行時のみ設定される）で確認する。

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/standup-progress-note/scripts/standup.py \
  new --date 9/18 --from /tmp/standup-2026-09-17.txt > /tmp/standup-2026-09-18.txt
```

新規に並べる場合は `--workstream` を繰り返す。ワークストリームは前回と同じ順、同じ名前にする。聞き手は前回と同じ順で聞く前提で待っている。名前を変えると別の話題だと受け取られる。

### 3. 各行を書く

上の表の順で並べる。1行は1文から2文にする。経緯と理由は落とし、結果と次の1手だけを残す。聞かれたら答えればよい。

### 4. 確認事項を足すか決める

その場にいる人が判断できることだけを書く。不在の人への確認は「誰々に確認します」と次の1手の行に書き、確認事項の行には出さない。

### 5. 検査してクリップボードへ入れる

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/standup-progress-note/scripts/standup.py copy /tmp/standup-<日付>.txt
```

`copy` は検査を通ったときだけ `pbcopy` する。検査だけを見たいときは `validate` を使う。ファイルはリポジトリに残さない。報告の正本は内部定例レポートの側にある。

## 書くときの注意

- 「対応します」「実施します」で終わらせず、何をどうするかを動詞で書く。聞き手は動詞から作業量を見積もる
- 前回言った期限を今回も繰り返すときは、なぜずれたかを1文だけ添える。前回より目標を狭めるときも、狭めたことを言葉にする。黙って狭めると、後から差分を指摘される
- 相手から指摘や差し戻しを受けた件は、相手の判断が遅かったという含意が入らない書き方にする。こちらの依頼の出し方に理由を置く
- 未確定のことを確定したように書かない。送信の有無、相手の了承の有無、レビュー依頼を出したかどうかは、確かめてから書く

## 罠

- 文字数は Python の `len()` で数える。`awk` の `length` や `wc -m` はロケールとバイト数の影響を受け、86 文字の行を 234 と報告することがある。検査スクリプトを直すときにここを変えない
- ヒアドキュメントから直接クリップボードへ流すと、検査を通さずにコピーできてしまう。`scripts/clipboard-guard.py` がこの経路を止め、`standup.py copy` へ誘導する
- フックはこの SKILL.md のフロントマターから登録される。`settings.json` には書かない。フロントマターに書いたフックは、スキルを呼んだ時点で登録されてセッションの残りで動き続ける。`settings.json` に書くとスキルを使わないセッションでも毎回走るため、スキル専用の検査はフロントマター側に置く
- そのぶん、スキルを呼ばずに報告を書いた場合はフックが登録されておらず検査されない。守れるのは、スキルを経由したセッションでエージェントがクリップボードへ入れる経路だけである
- フックの判定は、コマンド文字列に語が含まれるかではなく、実行位置で呼ばれているかで行う。文字列の一部で判定すると、フック自身のファイル名を含むコマンドをフック自身が止める。実際にこのスキルを作る途中で、`pbcopy-guard.py` というファイル名を置こうとして自己ブロックが起きた
- 報告本文には `#279` のような PR 番号が入る。`no-markdown` で `#` を全面禁止にすると誤検知するため、行頭の `#` だけを見ている
