# issue-driven-flow: tdd-cycle

TDD の Phase 0（設計）→ Red → Green → Refactor サイクルをガイドします。まずテストケース一覧を設計し、次にそれを 1 件ずつ Red-Green-Refactor で実装します。

## 手順

### Phase 0: テストケース列挙（Test Case Enumeration）

**ユーザーに実装したい機能を確認する**:

```
TDD サイクルを開始します。
実装したい関数・機能・振る舞いを説明してください。
（例: ユーザー入力を検証する validate_email 関数、メール形式チェックと長さ制限あり）
```

**テストケース一覧を設計する**（`tdd-enforce:test-case-design` スキルを参照）:

1. 引数・戻り値・分岐を分析する
2. 各入力因子を「正常系バリアント / 異常系 / 境界値」に分類する
3. テストケース一覧テーブルを生成して提示する:

```
## テストケース一覧: {機能名}

| 概要 | 件数 |
|---|---|
| 正常系 | N 件 |
| 異常系 | M 件 |
| 境界値 | K 件 |
| 合計 | N+M+K 件 |

### 正常系テスト（N 件）
| # | テスト名 | Given | When | Then |
|---|----------|-------|------|------|
| 1 | ... | ... | ... | ... |

### 異常系テスト（M 件）
| # | テスト名 | Given | When | Then |
|---|----------|-------|------|------|
| 1 | ... | ... | ... | ... |

### 境界値テスト（K 件）
| # | テスト名 | Given | When | Then |
|---|----------|-------|------|------|
| 1 | ... | ... | ... | ... |

このテストケース一覧でよろしいですか？
追加・削除・修正があれば教えてください。
```

4. ユーザーの承認を得てから Phase 1 に進む。

> **なぜテストケースを先に作るのか？**
> テストを 1 件ずつ書いていると「次は何をテストするか」が曖昧になり、正常系だけで終わりやすい。
> 一覧を先に作ることで、正常系 N 件 + 異常系 M 件 + 境界値 K 件 すべてをカバーするまで続けられる。

---

### Phase 1: Red フェーズ（失敗するテストを書く）

テストケース一覧の **1 行目**から順に実行する。現在の対象テストケースを明示する:

```
🔴 Red フェーズ（テストケース #1/N: {テスト名}）

Given: {入力}
When:  {操作}
Then:  {期待結果}

以下のテストを作成します:

[テストコードを表示]

このテストでよろしいですか？
```

ユーザーの了承を得てからテストファイルを作成する。テストを実行して失敗を確認する:

```bash
# テスト実行（言語に応じたコマンド）
cargo test / npx vitest run / pytest / go test ./...
```

失敗を確認:

```
✓ テストが失敗しました（Red 達成）
失敗内容: [エラーメッセージ]

→ Green フェーズに進みますか？
```

---

### Phase 2: Green フェーズ（最小限の実装）

テストをパスするための最小限の実装を提案する:

```
🟢 Green フェーズ（テストケース #1/N: {テスト名}）

テストをパスする最小限の実装:

[実装コードを表示]

この実装でよろしいですか？
```

ユーザーの了承を得てからコードを書き出す。テストを実行してパスを確認する:

```
✓ テストがパスしました（Green 達成）

→ Refactor フェーズに進みますか？（スキップも可）
```

---

### Phase 3: Refactor フェーズ（コード改善）

現在のコードを分析し、改善点を提案する:

```
🔧 Refactor フェーズ（テストケース #1/N 実装後）

以下の改善を提案します:
1. [改善提案1]
2. [改善提案2]

リファクタリングを実行しますか？（スキップも可）
```

改善がない場合はスキップする。リファクタリング後にテストが依然パスすることを確認する。

---

### 次のテストケースへ

1 件の Red-Green-Refactor が完了したら、一覧の次のテストケースに進む:

```
✓ テストケース #1 完了

進捗: {完了数}/{合計数} 件
次のケース: #2 「{テスト名}」（{正常系/異常系/境界値}）

続けて次のテストケースに進みますか？
  1. 次のテストケースに進む（Red フェーズ）
  2. 一覧を確認する
  3. 今日はここまでにする
```

すべてのテストケースが完了したら:

```
## ✅ TDD サイクル完了

実装した機能: {機能名}
テスト結果:
  - 正常系: N/N 件 ✓
  - 異常系: M/M 件 ✓
  - 境界値: K/K 件 ✓
  合計: {N+M+K} 件すべて Green

作成/変更したファイル:
  - {テストファイル}
  - {実装ファイル}

続けて次の機能を TDD で実装しますか？
  1. 次の TDD サイクルを開始（新機能）
  2. 現在の機能に追加のテストケースを設計する
  3. 終了
```

---

## 重要な原則

- **テストは必ず先に書く**。実装を先に書いてはいけない。
- **Phase 0 で一覧を先に作る**。1 件目の Red に入る前に全ケースを見渡す。
- **Green では最小限の実装のみ**。完璧を目指さない。
- **各ステップでユーザー確認**。勝手に進めない。
- **テスト実行は各フェーズで必ず行う**。Red で失敗確認、Green でパス確認、Refactor で回帰確認。
- **異常系・境界値を正常系と同数以上テストする**。正常系だけで終わらない。
