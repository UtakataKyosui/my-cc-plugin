# PR Triage 分類基準

## valid-fix（修正して返信）

以下のいずれかを満たす場合に選択する:

1. **具体的なバグ**: ロジック誤り、NullPointerException 相当、オフバイワン等
2. **型エラー**: TypeScript の型不整合、Null safety 違反、不正な型キャスト
3. **セキュリティ問題**: SQL インジェクション、XSS、認証バイパス等
4. **プロジェクトルール違反**: CLAUDE.md、コーディング規約、命名規則への違反
5. **明確な修正案あり**: レビュアーが具体的なコードを提示しており、技術的に妥当

**重要な検証ステップ**:
- `file_snippet` または `Read` で現在のファイル内容を確認する
- 指摘が今のコードに対して有効かを確認してから valid-fix にする
- すでに修正済みなら `invalid-reject` に切り替える

## invalid-reject（返信のみ、却下）

以下のいずれかを満たす場合に選択する:

1. **対応済み**: 指摘の内容がすでに現在のコードに反映されている（file_snippet で確認）
2. **誤指摘**: レビュアーの理解が誤っている（型定義、ライブラリ仕様、プロジェクトルールと矛盾）
3. **スコープ外**: 別 Issue/PR で対応すべき範囲
4. **意図的な実装**: コメントに書かれているパターンを意図的に避けている理由がある

`reply_draft` には却下理由を技術的根拠とともに記載する。「却下します」だけでは不十分。

## needs-human（スキップ、ユーザーに提示）

以下のいずれかを満たす場合に選択する:

1. **設計判断**: アーキテクチャ変更、API 破壊的変更、パフォーマンスとコード品質のトレードオフ
2. **意図不明**: 「この処理は必要ですか？」など質問コメント、議論を促すコメント
3. **大規模変更**: 多数のファイルにまたがる変更、テスト全体の書き換え
4. **コンテキスト不足**: file_snippet だけでは判断不能、外部情報が必要
5. **信頼度が低い**: どれにも当てはまらない、分類に自信がない

**保守的に判断する**: 迷ったら `needs-human` に倒す。false positive な自動実装より、人間の確認が安全。

## よくある分類の迷いどころ

| 状況 | 分類 | 理由 |
|------|------|------|
| 指摘は正しいが scope 外 | invalid-reject | スコープ外を明記した上で却下 |
| 指摘は正しいが設計判断が必要 | needs-human | 設計に関わるため人間判断 |
| コメントが質問形式だが修正が必要 | valid-fix | 指摘内容が明確なら valid-fix |
| 「〜はどうでしょうか？」という提案 | needs-human | 提案は設計判断を含むことが多い |
| 修正済みだが指摘が残っている | invalid-reject | 「対応済みです」と返信 |
| test ファイルのみの変更を指摘 | valid-fix | テスト修正も valid-fix として扱う |
