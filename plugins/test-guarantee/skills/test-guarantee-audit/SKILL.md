# テストの保証範囲の監査

テストの本数とカバレッジは、何が保証されているかを教えない。行が実行されただけでアサーションが振る舞いの変化を検出できないテストは、カバレッジ 100 パーセントでも何も保証しない。このスキルは、要求される命題の一覧と、テストが実際に保証している命題の一覧を突き合わせて差分を出す。

## 反例を出せない指摘は書かない

このスキルで最も重要な規則を先に書く。保証できていないと報告するには、その要求命題に違反しながら既存テストを通過する具体例を1つ挙げなければならない。

挙げる具体例は次のどちらかにする。

- 誤った実装。既存テストを通したまま要求命題を破るコードを、擬似コードで示す
- 具体的な入力値。その値を渡すと要求命題が破れるのに、既存テストはその値を試していないことを示す

どちらも示せない場合は、その指摘を推測として別の節に分ける。確定した欠落と混ぜない。アサーションをもっと強くできる、という形の指摘は具体例が無ければ書かない。この規則が無いと、監査結果は全テストに対する一般的な但し書きの羅列になり、読み手が確認する手がかりを失う。

## 手順

### 1. 要求命題を列挙する

Issue、仕様、受け入れ条件、型定義、docstring から、観測可能な振る舞いについての反証可能な文を取り出す。1つの命題は1つの文にする。

命題は「入力がこうであるとき、出力または状態はこうなる」の形に統一する。「バリデーションが正しく動く」は命題ではない。「メールアドレスに @ が含まれないとき、登録は拒否され error に理由が入る」が命題である。

要求が文書に無い場合は、実装を読んで命題を復元する。復元した命題は復元と明記する。実装から復元した命題は、実装のバグをそのまま要求として写す危険があるため、確定した要求と区別する。

### 2. 各テストが保証している命題を書く

テスト1件ごとに、アサーションだけを読んで保証している命題を書く。テスト名、`describe` の文字列、コメントは根拠にしない。名前は書き手の意図を表すが、実際に検出できる変化を表さない。

アサーションが無いテストは、何も保証していないと書く。実行されて例外が出ないことだけを確認しているテストは、例外が出ないことだけを保証していると書く。

### 3. 保証を破る実装を探す

各テストについて、そのテストを通過したまま対象の振る舞いを壊す実装を考える。見つかったら、そのテストの保証は名前が主張するより弱い。

よく見つかる型は `references/defeating-patterns.md` にまとめてある。監査を始める前にこのファイルを読む。パターン名を当てはめるだけで終わらせず、そのコードでの具体的な反例に落とす。

### 4. 3分類で突き合わせる

要求命題を次の3つに分ける。

| 分類 | 条件 |
|---|---|
| 保証済み | その命題を破る実装を書くと、既存のいずれかのテストが落ちる |
| 名前だけ保証 | それを検証すると称するテストがあるが、命題を破っても通過する反例を示せる |
| 未保証 | その命題を検証しようとしているテストが存在しない |

名前だけ保証を未保証と混ぜない。前者は読み手が保証されていると誤解している状態であり、テストが無い状態より危険である。書き足すべき内容も異なる。未保証にはテストの新規追加が必要で、名前だけ保証にはアサーションの修正が必要である。

### 5. 過剰な保証も報告する

要求命題に対応しないアサーションを見つけたら報告する。実装の内部構造を固定しているアサーションは、振る舞いを変えないリファクタリングでも落ちる。安全網ではなく作業の障害になっている。

## 報告の形

結論を最初に書く。要求命題の総数、保証済みの数、名前だけ保証の数、未保証の数を1文で示す。そのあとに次の順で並べる。

1. 名前だけ保証の命題。対応するテスト名、そのテストを通過する反例、必要なアサーションの修正内容
2. 未保証の命題。それを破る具体的な入力値、追加すべきテストが検証すべき内容
3. 過剰な保証。落ちる条件と、削るか書き換えるかの判断
4. 推測。反例を示せなかったが疑わしい箇所

各項目には対象ファイルと行番号を添える。反例は擬似コードか具体値で書き、文章で言い換えるだけにしない。

テストを書き足す作業はこのスキルでは行わない。何が足りないかを示すところまでが範囲である。追加するテストケースの洗い出しは `tdd-enforce:test-case-design` に渡す。

## 実行時の注意

テストスイートを実行して確かめる場合は、プロジェクト標準の入口を使う。`pnpm test` や `mise exec -- pnpm test` のように `package.json` の `scripts.test` へ委譲し、vitest や jest を直接呼ばない。ランナーの差分はプロジェクト側が吸収している。

テストが通っている状態を保証の証拠にしない。通ることは、そのアサーションが現在の実装と矛盾しないことしか意味しない。手順3の反例探しを省略できない。

対象を絞る。スイート全体を一度に監査すると、どの命題も浅くなる。PR の差分、1つのモジュール、1つの要求のまとまりのいずれかに区切ってから始める。

## 既存の TDD スキルとの分担

| スキル | 答える問い |
|---|---|
| `tdd-enforce` | Red-Green-Refactor をどう回すか |
| `tdd-enforce:test-case-design` | 何をテストすべきか |
| `tdd-enforce:formula` | 最低何本必要か |
| `tdd-enforce:ui-coverage-analyze` | 必要数に対して実際の本数が足りているか |
| このスキル | すでにあるテストが実際に何を保証しているか |

本数が足りていても保証が無い状態は起こる。逆に本数が少なくても要求命題を押さえていることもある。数を数えるスキルの結果とこのスキルの結果は独立に読む。
